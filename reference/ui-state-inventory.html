The state inventory

Every screen is more than one screen. This is the list you walk before you decide anything looks finished.

The five states

Scott Hurff's UI Stack, extending 37signals' earlier three-state solution. A screen is not designed until all five are.

StateWhenThe failure mode
Ideal Full, useful, working. The screenshot you'd put in the store listing. Designing only this one. It is the default, and it is the trap.
Empty No data at all. Three distinct causes — see below. A blank rectangle. The user cannot tell broken from new.
Error Something went wrong: bad input, dead connection, refused request. Losing what the user typed. Hurff: their input is sacred.
Partial Real data, but sparse. One row. Two photos. Half a profile. Layout built for abundance falls apart, and the user gives up early.
Loading Fetching, connecting, or moving between screens. No signal of progress, or a spinner that lies about how long.

Empty has three causes

They need different words on the screen. Collapsing them into one message is the most common empty-state mistake.

  • First use — nothing has been added yet. Teach and invite.
  • User cleared it — they emptied it themselves. Acknowledge, offer undo.
  • No results — the filter or search matched nothing. Say what was searched, and how to widen it.

What goes on an empty screen

Nielsen Norman Group's three guidelines. In order.

  1. Communicate system status. Say why it is empty. Never show “no records” while data is still on its way — a message that is contradicted two seconds later costs more trust than a blank would have.
  2. Provide learning cues. The empty screen is the best teaching moment you will get. “Star your favourites to list them here.”
  3. Provide a direct pathway. A button or a link to the thing that would fill it. Do not make them go and find the feature.

The procedure

Point this at one screen at a time. It takes about five minutes and it is the cheapest quality pass available.

  1. Name the screen and the one question its user opens it to answer.
  2. Walk the five states in order. For each, write the sentence the screen should say.
  3. Find the code path for each. If you cannot point at a file and line, it does not exist.
  4. For Empty, decide which of the three causes apply. Usually more than one.
  5. For Partial, check the layout at n = 1. Grids in particular.
  6. Write the misses down as issues. Do not fix them now — finish the inventory first.

Gotcha: grids at n = 1

The partial state's usual hiding place in CSS. These two look interchangeable and are not:

grid-template-columns: repeat(auto-fill, minmax(240px, 1fr));
grid-template-columns: repeat(auto-fit,  minmax(240px, 1fr));

auto-fill keeps the empty tracks it created. auto-fit collapses them, so the surviving items stretch to fill the row. With a full grid the two are identical. With one item, auto-fit gives you a single tile as wide as the screen.

Rule of thumb Want items to hold their size when there are few of them? auto-fill. Want them to stretch and fill the space? auto-fit. Decide it on purpose — most codebases have auto-fit because it was typed first.
