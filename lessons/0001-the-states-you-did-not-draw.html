Lesson 01 Building good web apps and UI ≈ 10 minutes

The states you didn't draw

Your board is careful about every condition you thought of. This lesson is about finding the ones you didn't — and there are two of them, sitting in your code right now.

Why this first

You said you want to build a good web app, and you picked all four layers: information design, visual craft, real conditions, states. We start here because state coverage is the layer where the gap between "built" and "shipped" is widest, and because it is the only one that can be made systematic. Taste takes years. A checklist takes ten minutes and catches the failures that make software feel amateur.

It also happens to be where your board is weakest — which is not obvious, because it is very strong everywhere else. That is normal. Careful people tend to be careful about the things they thought about.

The idea

In 2015 Scott Hurff named the thing designers keep getting wrong. We build the screen as it looks when everything has gone right — the app-store screenshot, the demo. He calls it the Ideal State, and it is a trap, because the other states then get "tacked on as an afterthought."

The world in which we live isn't perfect, and things go wrong. Scott Hurff, How to fix a bad user interface

His fix is a list of five. A screen is not designed until all five are. He calls it the UI Stack, extending an older 37signals idea that had only three.

  • Ideal — full, useful, working.
  • Empty — no data at all.
  • Error — something went wrong.
  • Partial — real data, but barely any.
  • Loading — on its way.

That is the whole of the knowledge. The skill is pointing it at a real screen without flinching, so let's do that now — at yours.

The audit

Five conditions your Fleet board can be in. For each one, decide from what you know of your own code: does the board handle it, or does it not? Answer before you look anything up. Getting one wrong is more useful than getting it right.

Partial A School pilots the programme with a single Drone. The Fleet renders one tile.

Missing — and this one is invisible until it happens. board.css:104 reads:

grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));

auto-fit collapses the tracks it has no items for, and the survivors stretch. One Drone on a laptop gives you a single tile roughly 1300px wide, holding a name, a badge and a battery bar. Change one word to auto-fill and the tile keeps its 240px.

Loading The board is opened and the first Fleet State has not arrived yet.

Handled. FleetBoard.tsx:28 guards on !state and shows the banner's connecting copy: "Waiting for the first Fleet State." Crucially it does not claim the Fleet is empty while it is still loading — which is exactly the trust-destroying mistake NN/g warns about, and you avoided it.

What the pattern tells you

Look at which three you got right and which two you missed. The three handled states — Ideal, Error, Loading — are all about the link. The two missing states — Empty and Partial — are both about how much data there is.

The finding You thought hard about the connection and not at all about the collection. That is the actual lesson here, and it is worth more than either bug: the states you cover are the states you worried about. A checklist is how you cover the ones you didn't worry about, and it is the only reliable way, because by definition you cannot remember to think of them.

Fix the empty state

Nielsen Norman Group give three guidelines, in order. Applied to your board, and using your own vocabulary from CONTEXT.md:

  1. Communicate system status. Say why it is empty, in Teacher language, without borrowing a Status word: "No Drones have been added to this School yet." Not "no data", not "empty fleet".
  2. Provide a learning cue. Say what would fill it — that every Drone the School owns gets a tile here, switched on or not. This is your best chance to teach that the board shows the cupboard, not the sky.
  3. Provide a direct pathway. A link to however registration actually happens. You need to decide this one — the roster is passed into GroundStation at construction, so today there is no in-app route to add a Drone. That is a genuine product question, not a CSS one. Ask me and we can work it through.

Where it goes: in FleetBoard.tsx, between the guard at line 28 and the grid at line 44. Note that this is a distinct branch from the loading guard — the two must not collapse into one, or you reintroduce the mistake you currently avoid.

One judgement call

Should FleetSummary still render "0 of 0 ready" above an empty state? Your FleetSummary comment argues the attention count must be present at zero so a change reads as a number moving rather than an element appearing. Does that argument still hold when the whole Fleet is empty, or is "0 of 0" just noise on a screen that has already explained itself? There is a defensible answer either way — have one.

From memory

Retrieval, no scrolling up Name all five states of the UI Stack. Say them out loud — the effort of pulling them back is what makes them stick, and re-reading the list would feel like learning without being it.

Ideal, Empty, Error, Partial, Loading.

If you missed one, it was probably Partial. It is the one with no obvious moment of failure — nothing throws, nothing disconnects, the layout is just quietly wrong. It is also the one you missed in your own board.

Three questions

A dashboard shows "No records found", then fills with rows two seconds later. Which guideline did it break?

It reported a state that was not true yet. NN/g single this out because a message contradicted seconds later costs more trust than a blank would have — the user now knows the screen is willing to lie. It is the Loading state wearing the Empty state's clothes.

One Drone is left in the Fleet. Under repeat(auto-fit, minmax(240px, 1fr)), that tile renders…

auto-fit collapses the empty tracks, so the one surviving track takes the whole 1fr. auto-fill keeps the empty tracks and the tile stays 240px. With a full grid the two behave identically, which is why this survives review — it only diverges when the data is sparse.

Hurff splits Empty into three causes. Which is not one of them?

A refused request is the Error state, not the Empty one. The three causes of Empty are first use, user-cleared, and no results — and they want different words on the screen. Your board's empty state is the first kind.
